# KEMI Box Linux 优化

先确认设备、实际运行包和源码提交。101 为 ARM64，88 为 amd64，具体身份、glibc 和当前运行用户现场回读。沿项目原仿真或可信备用通道操作。备用 SSH 若登录另一用户，只用于核实状态，桌面启动和 Keyring 验收回到原桌面用户。设备恢复复用 [bot-kemi-box](../bot-kemi-box/SKILL.md)，通用构建和验收复用 [linux-desktop-build-acceptance](../linux-desktop-build-acceptance/SKILL.md)。

## 构建与容量

- 大量写盘前用实际目标卷的可用字节减去项目保留线。估算剩余编译对象、临时链接输出和打包副本各自的峰值。带符号对象、解包依赖及打包目录经常远大于最终压缩包。旧版成品大小只作量级参照。
- 内存触发保护后，读取构建器的业务回执、退出原因和原子进程状态。systemd 显示 succeeded 也可能只是外层控制器成功写完失败回执。确认终态后保留合格增量对象，使用独立续建回执，按证据降低并发，并同步调整顶层 make 与子构建并发。 单任务编译仍可能触及单个链接器的内存峰值，链接阶段同时观察实际链接进程的 RSS 和全机可用内存。 中断链接后核对目标库及导出清单。零字节残留可能让增量构建跳过主库并在下游报未定义符号。核对原事务终态、文件大小和活动引用后，仅移除已证实无效的生成文件，再核重新生成的 ELF 和符号。若剩余空间不足以通过原门槛，先处理有证据的闲置生成物。
- 单个 GCC 编译单元已在串行构建中触发全机内存保护时，先确认失败对象已回收并保留成功对象。可用隔离编译器包装器，只给该源文件追加 GCC 垃圾回收参数，其他命令沿用原编译器和参数。101 的 KOFFICE Writer 在 GCC 15.2 上实测 `--param=ggc-min-expand=10 --param=ggc-min-heapsize=32768` 后生成 `paintfrm.o`，并继续编译后续对象。核真实编译进程参数、非空对象和下一构建动作，保留原系统内存门槛。该结果只证明这一编译单元通过，完整引擎和链接仍按各自回执验收。 如果同一模块的不同编译单元连续触发相同保护，可将已验证参数限于该模块尚未编译的源文件，保留已完成对象并预期单文件耗时增加。101 的 Writer 后续在 `unostyle.cxx`、`docsh2.cxx`、`swdtflvr.cxx` 和 `PostItMgr.cxx` 均验证生成非空 AArch64 对象，R14 的后续 Writer 编译日志也确认参数继续生效。运行保护与链接、打包验收各自保留。 如果 Release 配置仍为所有对象生成调试信息，且单文件调低 GCC 回收阈值仍触发保护，可仅对失败单元在原参数最后追加 `-g0`。101 的 `textsh1.cxx` 实测生成 728,968 字节的 AArch64 对象，`readelf -SW` 未见 `.debug_info`，后续 Writer 单元继续原参数。记录该对象失去调试信息的取舍，单独验证最终链接、符号和实际功能。
- GNU ld 的低内存选项仍触及保留线时，可在私有 SDK 验证并锁定兼容的 LLD。先用同架构小样核原链接参数，再只对失败目标注入链接器和线程数，从实际进程参数确认生效。101 曾用单线程 LLD 21 完成约 2.28 GB 的主库链接，随后验证 AArch64 ELF 和此前缺失的导出符号。链接可能以临时文件写入，观察实际占用及最终产物，整套引擎仍按自身回执验收。
- 链接被内存保护中止后，即使共享库大小和 ELF 头看起来正常，也要核目标的有效 Build ID（若配置要求生成）、动态符号及后续组件登记。101 的 KOFFICE Calc 留下约 792 MB 的 GNU ld 残件，Build ID 节没有有效值。保留对象，只清除确认无引用的残件，随后用私有 SDK 中的 LLD 21 单线程和目标级 `--strip-debug` 得到约 28 MB 的 AArch64 库。用 ELF `.comment` 确认实际链接器，再核 Build ID、导出符号和冻结引擎版本。链接通过后仍须等后续编译和引擎终态。[101 Calc 链接证据](https://github.com/caucy2026/kemi-office/commit/c83a8f13d68f93c2cb0cf1021145c65bf98986db)
- 大目录先按源码、工具链、可再生输出、正式包和当前引用分开。清理旧 Cargo 输出前核实构建终态、目标路径、活动引用、保留的源码和验收证据。硬链接要核 inode 和链接数。下载残片只有在完整归档符合锁定 SHA 且残片可证明冗余后才清。 清理 Cargo registry 解包缓存前，可逐包验证保留的 .crate 与 Cargo.lock 的校验和一致，再比对解包目录的文件树和内容。Cargo 自建的 .cargo-ok 可单独排除。核对挂载和进程引用后，只清理可重建的 registry/src，保留离线 .crate 与索引。逐批回读删除路径和目标卷可用字节，复用 [kemi-storage-cleanup](../kemi-storage-cleanup/SKILL.md)。
- 隔离 SDK 中验证实际工具和依赖。若 Qt 使用编译期引擎绝对路径，可把已完成的引擎只读绑定到隔离环境内的正式安装路径，configure 后核生成的路径，再编译。最终包从正式位置冷启，并核对实际映射的库。保留原设备 glibc 基线，私有运行库同时检查 GUI 和 sidecar。

- 磁盘紧张时，先按已分配字节量取安装树，用 `readelf -SW` 抽样识别大 ELF 的调试节。在有明确空间上限的隔离目录，对实际库用 `objcopy --strip-debug` 生成副本，再用 `readelf --dyn-syms --wide` 和 `readelf -d` 比对动态符号与依赖。101 的 KOFFICE 已在实际 UNO 库验证上述检查及归档成员哈希。整包若计划逐件压缩，先测输入、临时文件和最终归档的叠加峰值，避免完整复制安装树。整包仍需校验归档、冷启动和实际加载。
- 私有运行时使用打包所用的 loader 对引擎、GUI 和子进程分别执行 `--list`。按实际解析路径去重统计依赖容量。Qt WebEngine 另核 `QtWebEngineProcess`、插件、资源包、V8 snapshot 和语言文件。101 的 KOFFICE 已测得侧车直接库约 322 MB。按需加载的依赖在最终包实际启动时补验，检查进程映射和目标机兼容性。

- 外接构建卷掉线并重新挂载后，Lima 宿主代理可能仍存活、端口仍监听。先核 SSH 握手、`limactl list --json`、管理套接字，以及 `lsof` 的 revoked 句柄。用宿主磁盘卸载和重新挂载的时间对照代理日志，记录原任务回执。卷重新可写后，继续核对客机磁盘及原任务状态，再按原路线恢复。已确认完成的构建复用原产物和哈希，结果未知的任务先对账。

- 旧烟测目录同时有解包件、改版二进制和会话状态时，可用 `dpkg-deb --fsys-tarfile` 流式读取已保留、SHA-256 匹配的原包。逐件核普通文件哈希及符号链接目标，记录不一致项。核挂载和进程 cwd、exe、fd、maps 后，冻结确认相同的文件身份，删除前复核并逐件回读。101 已用该方法清理 26,168 件，保留两处不同的二进制、原测试包、烟测 HOME 和证据。保留目录空间回执以及仍可从原包恢复的输入。

- 构建准入遇到其他编译、内存不足或磁盘不足时，用结构化结果和受控非零退出码返回。101 的 Ubuntu Apport 曾将预检的未捕获断言记成崩溃。验证忙和资源不足两种结果均在创建构建目录前退出，并保留真实异常的可追溯日志。[传书 168 实测](https://github.com/caucy2026/kemi-send/commit/0bc0de4e7370855964f97ef0dd37a4780fb7fa3b)

- 在 Ubuntu 20 真机依赖 systemd 内存上限前，先核内核是否启用并挂载 memory cgroup，再核运行进程实际所在组的有效限制。101 曾显示 `MemoryAccounting=yes` 和 `MemoryMax=805306368`，但内核无 memory 控制器，Dart 分析进程实际触发全机 OOM。目标机不能执行资源上限时，使用有足够内存的隔离环境完成静态分析，目标机保留给运行验收。结束时对照同 PID 的内核记录和业务回执，区分全机 OOM、组内限额和程序错误。

## 性能与硬件验收

- 性能对比固定设备、实际包、输入和操作顺序。秒表检查前台动画和真实输入连续性，资源采样涵盖完整进程族。严格空闲时记录 PSS、单核等效 CPU、监听进程及仿真实调。项目的 G6 与帧间隔门槛沿用原验收规则。
- H.264 与 H.265 分别验真实双机协商、发送端硬编、接收端硬解及持续出帧。将日志、硬件组件和实际帧绑定到同一会话及候选包 SHA。单独硬件探针可定位能力，产品会话仍须验收。
- ARM64 OMX 先实测组件支持的像素格式，再统一探针与产品输入。101 已见 NV12 被编码器拒绝而 YUV420P 可用，也见首个访问单元未立即出帧。接受输入但暂时无输出时采用有界等待。解码端按实例管理回调、端口重配、缓冲回收和 EOS，能力广告须收到实际可用帧。新分辨率或厂商格式先用已知色度样本核验。

## 应用交付

- 同一 Linux 下载包可包含 amd64 和 arm64 两个载荷。核外层哈希后按实际架构流式取对应成员，再验证内层哈希、包名、版本和架构。两机以同一外层 SHA 验证安装、自更新、冷启与功能。
- 本机版本从安装登记或系统元数据读取。Debian Version 可独立显示，商城构建号用于更新判断。AppImage 登记完整版本名，旧登记仍可显示构建号。实测应用中心安装、打开、卸载、复制下载链接、二维码和关闭。卸载前确认实际归属和运行状态，保留用户数据。
- 登录自启在原桌面用户下验证实际重登、单实例、仿真实调与原 Keyring 可用性。安全凭据不得进入证据。扫码验收区分公网协议、实际手机扫码和原字段回填，各自记录结果。

- 多个客户端共用同一 AppImage 安装登记时，按稳定包 ID 使用同一个锁路径。把版本复查、暂存、启动交接和原子登记写入放在同一临界区，保留锁文件的 inode。101 已验证三个候选安装器的并发防降级。运行识别可核对 FUSE 进程的可执行路径与 GUI 的 APPIMAGE 环境项，权限受限时把无法确认的状态单列。真实启动、旧版客户端混用与卸载需分别验收。
- 仿真 SSH 命令长度按控制端实现核对。101 实测 8192 个 ASCII 字符通过，8193 个在执行前拒绝。长测试夹具走同通道的文件上传，先核上传及设备回读 SHA-256，再用短命令执行。适合小型夹具的临时文件系统可以隔离测试输出，执行结束按精确路径核验并清理上传件与设备夹具。

- 仿真失联先用已登记备用通道核当前运行包、进程和 relay 的 ELF 依赖。分别读取应用开关、relay 开关和就绪状态。101 的 773 因缺 libyuv.so 无法启动 relay，补齐后可读协议，但应用仍在启动阶段超时。发布时用目标基线按包内库路径验实际加载；工具输出解析固定 C locale。恢复后要用原设备 ID 实际调用工具。
- 钥匙环弹窗排查先在同一桌面会话只读核对 Secret Service 的 default/login/session alias，避免打印凭据。101 只有会话集合时，旧 secret-tool store 可能请求创建钥匙环。无提示读取须区分锁定与缺失，写入只用既有集合并拒绝返回的提示请求。隔离 D-Bus/HOME 分别验证缺默认、已解锁、锁定和第二会话冷读；原桌面点击及覆盖升级另验。

## 持续更新

每次验证完可复用的新方法，随本次工作更新此技能及团队技能仓库。项目记录保留设备与包标识、源码提交、原事务、输入、实测结果、清理回执及未验项。技能只记录通用做法、适用条件和失败信号。未完成实机验证的方法明确标为候选。发现旧方法已被证据推翻时，更新原段并链接项目记录。
