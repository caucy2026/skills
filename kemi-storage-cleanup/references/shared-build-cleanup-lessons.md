# 共享构建目录清理：实测方法与效率复盘

适用于多个同事共享源码、独立构建快照、APFS 克隆副本较多的开发环境。路径、版本、时限和保留集合必须按现场更新，不把本案例参数作为永久规则。

## 1. 最有价值的方法：先冻结保留集合，再生成删除清单

先确定当前任务真正使用的源码、构建目录、正在传输的包、最新交付包、独立回滚包及证据目录。将这些精确路径列为保留集合；“旧版本号”“两天前”“没有进程”都不能独立证明可删。

先读接续文档、当前交付合同及活动任务状态。当前源码、包 SHA、签名及回滚点比目录名称可靠。只读查询其他会话不等于允许发消息；需要跨会话询问时复用用户明确的协调授权，合并为一次精确问题，要求对方在原会话回复即可。没有回复不是同意，不反复打断同事。

对其余内容记录四类：

- 可清：明确生成来源、已不用、位于授权范围内的编译缓存。
- 保留：手写源码、Git/未提交状态、依赖输入、配置、证据、签名材料、正式包、回滚及当前产物。
- 待核：用途、归属、引用或是否有完整可恢复副本不明。
- 被阻断：工具拒绝的精确动作与理由；不混入下一批自动执行。

## 2. 用一次有界盘点代替反复全树扫描

1. 读取本机 AGENTS/LOCAL-ENVIRONMENT-RULES 和当前项目记录。用 `df -k` 记录所在文件系统可用空间。
2. 先测用户点名的目录及直接子目录（`du -k -d 1`），结果写到文件供后续复用。只有最大的混合目录需要进一步到第二层。不要同时启动多个覆盖同一目录的 `du`。
3. 盘点结果分开报告：整个项目、历史构建、可清文件、保留内容。父子目录大小不能重复相加；不把所有项目共享缓存计入本项目。
4. 从最大的可清子树冻结文件清单，检查任务引用和精确进程路径，再做有界打开文件核验。

本次低效做法：对三十多个含完整 runtime/node_modules 的源码快照逐个 `lsof +D`，占用检查约十分钟；全缓存扫描长时间无输出。下次对候选文件分批或更小的生成目录做定向检查，先用进程参数/当前依赖排除活动根。给只读扫描设置合理时限；超时应记为未知，不是无占用。若终止扫描，仅终止自己启动并确认 PID 的扫描任务，不结束构建/签名/传输。不得为省时间跳过必要占用核验。

## 3. 年龄、授权与并发写入必须落到清单

“超过两天”默认按扫描时刻往前48小时的文件 mtime；记录截止时间、时区和扫描时间。目录 mtime、名字里的日期及版本号不替代文件 mtime。

用户扩大到“近期已不用缓存”时，更新授权记录和清单选择条件，保留旧批次。不要悄悄移除年龄检查后重用旧的全量清单。没有活动进程只是必要证据之一；仍需核对当前构建依赖、包清单/符号链接和保留记录。无跨快照引用不能证明未来绝不会使用，存在不确定性时保留该项。

建议清单字段（按需要使用，不要求引入新系统）：

```
path, category, retainedSourceOrArtifact, reasonUnused,
sizeBytes, allocatedBytes, device, inode, mtimeNs,
scanTime, cutoffTimeOrAuthorizedWindow, openFileCheck,
keepSet, decision, outcome
```

执行时仅处理已批准清单，重新核对规范化路径、文件系统、inode、大小、mtime和占用；变化或消失的文件跳过并记录。不要跟随目录符号链接越界；拒绝路径中符号链接、路径替换等无法安全核实的目标。对仍可能写入的目录暂不清理，不能把 stat 后再 unlink 的检查说成无竞态保证。

同一磁盘的删除批次顺序执行，每批完成后测空间。只读检查可以安全并行，但并发删除会使释放量归因混乱。保留清单和结果应落在不会被删除的文档/证据位置，不仅保存在临时目录。

## 4. Flutter/Rust/Xcode 的具体区分

- `.tmp/cloud-main` 可能是完整源码/Git快照；只处理核实的生成文件，不整目录删除。
- `.dart_tool/package_config.json`、`package_graph.json` 等冻结依赖输入保留。之前隔离构建漏 package_graph 导致返工，不应为了省几KB重演问题。
- `.dart_tool/flutter_build/<hash>/<arch>/snapshot_assembly.S` 可为 Flutter AOT 自动生成汇编。核验生成路径、Dart快照符号（例如 `_kDartVmSnapshotInstructions`）及保留源代码/工具链后才列为生成产物；不能按 `.S` 扩展名全盘删除，不能删除手写汇编。
- `.o/.a/.dill/.pcm/.rmeta/.rlib` 只是筛选线索，仍需确认位于生成目录且来源可重建；第三方交付库、当前运行依赖不因扩展名相同而可删。
- `node_modules/**/build/` 可以装着必需 JavaScript 运行代码。严禁递归按名排除所有 `build`；已有事故曾因此让签名、公证通过的 App 启动失败。仅锚定已核验的生成路径。
- Rust target 中有测试日志、生成代码和配置时逐文件分类，不删除整个混合目录；当前 target 和共享工具链保留。
- 旧 `.app`/ZIP/签名候选不因版本旧自动可删。需要清验证副本时先验证保留归档可恢复相同内容，身份/字节证据齐全；正式和必要回滚包继续保留。
- 裁剪过的历史构建目录必须标记“输出不完整，需重建”，不能再当可运行安装包或完整回滚点。不要只删除主程序就声称一个旧版本已安全归档。

## 5. APFS：以可用空间变化验收容量目标

同时保留三个数：逻辑文件字节数（st_size）、分配占用（st_blocks × 512）、同一文件系统可用空间变化（df 或 statvfs）。分配占用也不是独占块大小；APFS克隆共享、硬链接、快照、打开的已删除文件以及其他任务写入都会影响结果。

GiB = bytes / 2^30；GB = bytes / 10^9。用户要求“100g”时明确报告使用的单位，不把56GiB文件占用写成释放56GB。

案例：2026-10-03 VibeKits删除49,516个旧生成文件，分配占用合计56.146GiB；外盘可用从3.473至23.306GiB，观测净增19.833GiB，即21.295GB。100GB目标未达。因存在并发活动及共享块，不能断言差值全部由某一个因素造成，也不能把各批次前后差叠加成独立贡献。

每批后按实际净增评估下一候选，达到目标就停止。安全候选不足或平台阻断时明确缺口，不删除源码/回退点凑数字，不宣称达标。

## 6. 工具拒绝：只增加实质证据，不反复换壳重试

本次近期约50GiB编译清单未执行：自动审批认为缺少充分的已不用证据/年龄边界；补充552/528当前依赖隔离后仍被拒绝。这个结果是失败边界，不是可推广的清理成功方法。

有效后续应是缩小到可获准范围，或取得确实改变风险判断的证据（例如负责人精确保留清单、完整恢复资产的校验）；仅换脚本名、删除过滤条件或重申用户目标不解决拒绝原因。不得绕过拒绝。已经取得的有效授权要记录复用，不因进入下一批而反复要求用户“允许”；平台仍阻断时说明精确原因，继续未受阻工作。

## 8. 同事仍工作时的复查补充（2026-10-03）

只读复查实际发现：日期较旧的hbbv `final-server` 目录仍是服务运行目录，包含数据库/配置/TLS材料；PAD旧命名Gradle目录仍被守护进程占用。Mac继任者继续修输入焦点和启动，不因当前无编译器就删除其恢复/续建输入。由此将“缓存内活跃服务”和“任务计划依赖”与进程打开检查一起列为保留依据。

先前约50GiB近期编译候选复查仍存在，但未取得可放行证据，本轮没有删除，也没有重复提交被拒范围。可优先核对的对象依次是已结束构建的对象/模块缓存、匹配保留归档的重复验包二进制、新达到时限的旧生成文件。三者均需各自证据，不能直接把类别当可删清单。

源码及文档无论在何处全部保留，包括未提交源码、历史源码快照、生成文档和验收记录；不能因云端已有备份或用户要求释放容量而删除。只有明确生成且可再生的非源码/非文档文件才可能进入删除清单。
