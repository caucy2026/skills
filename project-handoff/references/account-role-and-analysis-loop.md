# 账号、角色对齐与最有效的重建闭环

这是SWDOL接手补充。实际连接/查询复用项目已成功只读脚本和授权凭据读取器；不新增连接体系、不猜密码/库名/字段、不使用原版在线写库来凑前态。接手者可在已授权测试范围重新查当前账号/角色，不需要为同类只读查询重复审批。需要更大操作时依现有授权边界判断。

## 交接者必须给出的查找入口

- 当前后台地址/服务与数据库版本、已验证只读查询执行器的绝对路径/SHA、所用连接配置与私有凭据提供器位置、调用范例和成功结果格式。不得把密码写入argv、截图、网页或GitHub。
- 数据库schema证据、账号与角色映射文件、最近两次只读一致结果、角色页/入图原帧与协议/后台关联证据。缺执行器或schema就写交接缺口，不能仅写“去查数据库”当交清。
- 常用资料：server/DEVELOPMENT_STATUS.md、DOCUMENT_RECONCILIATION_20261001.md、最近原版账号注册/角色前态记录及DataCenter/登录合同。目录按实际根发现；dataCenter.ini与MasterServer.ini用途不同，不拿错误配置字段猜连接。

## 从账号查角色，再从角色反查账号

1. 核当前数据库和连接真实身份，只读发现表/字段。原MySQL3.23可在已验证连接执行器使用 `SHOW TABLES`、`SHOW FIELDS FROM useraccount`、`SHOW FIELDS FROM charpool`；仅取元数据，不输出全表密码。SQL Server crossgate独立核 `Member_Data_Table`/`Member_Login_Table` 已有schema和认证合同，不能因MySQL有账号就判断Master一定可登录。
2. 以授权账号的精确账号键查询账号行，只选身份/状态必需列；按实际schema中的账号关系键去查charpool角色，记录RoleID、原RoleName字节/HEX、种族/性别/职业/等级、Section和必要前态。同名或大小写/编码关系不明确则拒绝任选第一行。
3. 原版charpool的AccountID与RoleID、RoleName是不同层。只有当前schema和原合同确认字段关系后才用参数化形状 `SELECT RoleID, HEX(RoleName), AccountID FROM charpool WHERE AccountID = <bound_account_key>`；反查形状 `SELECT RoleID, HEX(RoleName), AccountID FROM charpool WHERE RoleID = <bound_role_id>`。这些是schema确认后的模板，不是无凭据即可运行的万能命令；参数由执行器绑定，不拼未经校验输入。目标表字段若不同，遵实际发现而不是硬套模板。
4. 角色槽位由真实登录选择列表与当前绑定确认，不按RoleID顺序猜左/右槽。正常登录→选角→实际入图后，核角色名原字节、Section、当前会话/PID/actor代次与后台RoleID关联。原账号认证若“正在使用”，先核自己的会话是否仍在；不踢别人、不清全租约。
5. 若从可见演员反查，先核演员类型、实例/运行句柄、地图与创建代次，再追真实后台玩家RoleID；NPC/Object模板、observer-local handle、party/chat runtimeId不是数据库角色ID。不能只用名字、位置或裸指针认身份。
6. 为每个测试角色保存私有对齐表：原账号键→原RoleID→真实选择槽→本轮session/Section/actor代次；我方principalKey→roleSlot→角色不可复用代次/来源RoleID映射。principal、slot、模板/ObjectID与observer handle都分别保存。槽删重建会复用，不能把旧称号/奖励/审计归到新角色。
7. 必要前态按RoleID从charpool、bodyitemstable、bankitemstable、magictable、magiceffecttable等已确认表窄读两次，保留列顺序、原始二进制/GBK字节和哈希；变化则不可比较。两次一致的MyISAM查询不是跨表ACID快照。只在我方独立私库回放，不写原服角色HP/材料/坐标凑一致。

## 原版私有前态副本的具体限制

项目 `tools/import_original_role_snapshot.py` 可把已采集的只读双读稳定五表JSON转成私有字节保真SQLite，调用形状 `python3 <project>/tools/import_original_role_snapshot.py --input <private-source.json> --output <new-private-reference.sqlite>`。它不是在线查询器，也不是我方LIS/LRS转换器；当前实现固定校验RoleID95，新角色不能直接套用。输入必须有columns与valuesBase64，已有目标拒绝覆盖，输出需回读哈希。其它RoleID用现有经验证通用入口；没有就先记录缺口/核通用化，不靠改原库或换角色隐瞒失败。这个具体限制来自当前源码，不把它称任意角色导入全流程。

## 最有效的研发方法：边操作边观测，再重放差分

1. **问题先明确。** 选择当前未闭合的一项，例如菜单取消、扣材料、Boss回血、范围目标或交易即时保存。先读最新合同和纠错，锁原EXE/资源/数据SHA及切片，写预期/候选解释与能区分它们的最小动作。
2. **两端准备齐。** 正确账号/角色/初态、健康后台唯一owner、前端当前PID及输入、前后台必要探针、单collector、原始截图和有界日志目录同时准备。按成熟技能恢复，三分钟超时立即停试错回查文档；不在这一步无界耗时。
3. **真正触发。** 用原版或我方客户端正常登录、走路、选择、施法/攻击/对话/交易；MCP公共输入触发真实路径。前端记录输入消费与实际出包，后台记录解析/目标/条件/状态/事务/发布，不直接造成功回包或改HP/坐标。
4. **对齐事件。** runId、UTC/单调序列、角色/会话代次、地图实例、对象句柄映射、opcode/request、指令位置串起：输入→客户端校验→请求→后台裁决→状态→持久提交→发布→前端应用→可见结果。DLL加载和心跳不是业务事件；缺探针覆盖不能判断业务未执行。
5. **静态动态一起拆算法。** 动态指出实际分支/字段/时序；静态追调用者、参数与所有者、失败、RNG/时钟、资源来源。互相冲突先反查，不迷信旧文字；写通用typed合同，区别观察/推导/未知。比如范围中心、成功计数或变量prefix曾需原字节纠正，不能凭经验改180/概率/地图特例。
6. **定位客户端或服务器。** A原版客户端→原版服；B同轮完整我方客户端→原版服；C与B同程序/资源SHA→我方私服。同前态A/B差异查输入/显示/协议，B/C差异查通用后台算法/保存。D原版客户端→我方服是长期终验。诊断夹具或强制RNG只记隔离用途，不充自然剧情/Boss通过。
7. **修后完整闭环。** 修改前查直接/间接依赖，后用同一APP/BIN复跑正常、拒绝、重复、断线、重登、在线服务重启及受影响旧案例。剧情核材料/金币/Mark/称号/装备即时DB；战斗核HPMP/控制/仇恨/死亡掉落重生；同步核本人/远端/下线。原始前中后画面可单独放大，时间相位和真实差异保留。
8. **交回材料与收现场。** 对应专题/执行账/网页记录已完成、未完成、证据、算法来源、失败原因、下一操作和通过条件。停本轮采集、归档回读、精确清不用文件、核空间及健康；两小时窗口按用户要求报告和选择性GitHub备份、回读远端SHA。没有整门增量不涨百分比，报告后继续完整目标。

接手者必须实际重做至少一个已授权最小闭环，才能证明会查身份、会恢复、会触发并关联事件。写技能不等于全部环境已恢复，也不保证所有目标已完成。
