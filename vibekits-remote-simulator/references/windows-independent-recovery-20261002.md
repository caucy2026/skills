# Windows 独立恢复方案与验收标准

日期：2026-10-02。目的：解决电脑和SSH仍可达、VibeKits主程序却不能仿真的现场。这里规定下版交付要求，不表示已安装到58或所有恢复功能已完成。

## 必须保留的三层恢复能力

1. **正常仿真通道**：使用原设备ID、原安装身份和既有允许/拒绝名单，执行日常任务。
2. **独立恢复入口**：主程序起不来或Harness初始化失败时，仍能用同一设备身份查询恢复状态、取升级日志、启动已核验程序、恢复上个已验证版本。它只支持固定恢复动作，不提供未经授权的任意命令执行。已有信任继续有效，黑名单继续拒绝；未知设备仍需目标人员首次确认，不能因为叫“恢复”就绕过授权。
3. **本机签名恢复工具**：独立入口也不可用时，目标电脑的人或已有办公通道只需启动一次“修复VibeKits”工具，读取真实现场并执行受限恢复。若电脑关机、网络不可用或所有入口停止，不能承诺只凭ID远程恢复。

独立恢复入口须从既有原生relay演进，并由独立生命周期管理器持有唯一实例；不得同时启动两个相同ID的relay争抢注册。主程序、任务Harness、升级器与恢复入口的就绪状态分别上报。不能把服务器在线、SSH监听、集群心跳或cached connected当成全部业务可用。

恢复组件放在主App替换目录之外，使用与正式软件相同可信签名发行，不依赖Flutter/Harness模型Key、在线下载、PowerShell7或运行未签脚本。必须在Windows10/11既有执行策略下实际测试；不能通过Bypass或关闭安全策略适配。若使用用户级启动，验证注销/登录与重启恢复；若需要系统服务，则只在明确安装授权和平台确认后配置，保留已有正常SSH服务，不擅自改变其端口或ACL。

## 有限恢复动作与流程

- status：报告主机身份、原ID、实际文件/运行版本、主程序/relay/SSH状态、磁盘空间、最近升级AttemptId和错误阶段；仅脱敏日志，不返回Key、token或私钥。
- collect_logs：读取该次安装终态、崩溃/组件缺失、SSH配置验证和原生gate错误。证据先取得，结果未知不重复安装。
- start_verified_app：仅启动固定安装目录中已验证签名和hash的正式App，使用原交互用户；不能将Session0进程存在当GUI可用。
- restore_last_good：核验完整旧包manifest/hash、同签名身份和回退事务，停止精确候选进程，同卷完整目录替换，恢复匹配的应用版本登记，再启动旧版；不合并新旧DLL，不清用户数据、登录、设备信任或ID材料。
- verify_original_channel：原ID认证后实际执行命令、文件传输及原房间重连。失败保留故障现场和状态，不能只写“已修复”。

所有恢复动作关联请求ID、原设备ID、升级AttemptId、动作阶段、签名/hash、旧/新版本及回执；重复请求先查已完成动作，防止重复替换。正常任务执行权与受限恢复操作分开管理，恢复入口不能扩大任务工具许可。

## 自动升级事务

顺序必须是：盘点现有功能与授权 → 同卷完整旧包备份和版本登记快照 → 独立守护确认正在运行 → 替换候选 → 原ID真实健康验证 → 提交。独立守护尚未启动、备份未验证或空间不足时拒绝开始升级。

守护超时或App崩溃/关键文件缺失：若安装器仍运行则记录并进入有限等待，不强行覆盖；若事务身份或候选文件被第三方改变，则停止自动覆盖并保留证据；其他已核验失败则恢复旧包。健康提交必须来自本次AttemptId，不能凭历史回执或模型自述。更新器/守护崩溃和断电后，独立入口读取持久事务阶段继续对账，不盲目再次安装。

## 当前实现与缺口

- WindowsClusterUpdateService 已补实际EXE/注册表build一致性，以及完成后重新核验，定向16项回归通过；未签名部署。
- Watch-VibekitsUpgrade.ps1 是守护候选，已有路径、hash、签名、超时、完整目录恢复门禁。此次补上安装过程中主EXE或目标目录缺失时的恢复处理，避免Get-FileHash先抛错而无法恢复。
- 候选尚未成为独立签名可执行恢复组件，未集成正式安装器；xzl现有策略拒绝未签脚本，不能下发后宣称已可用。
- 守护尚未实现安装登记快照恢复、持久事务断电恢复、独立原ID恢复入口或已认证健康回执的正式协议。以上全部是发布阻断项，不以设计文档替代代码验收。

## 逐项验收

| 编号 | 故障/流程 | 通过条件 |
| --- | --- | --- |
| R01 | 正常覆盖升级 | 原仿真/办公ID不变，旧授权直接可用；真实命令/SFTP/房间重连后才提交 |
| R02 | 主App崩溃或不能启动 | 独立入口原ID仍可查询，取得真实错误，恢复旧版后实调成功 |
| R03 | relay可注册但Harness未就绪 | 后台明确显示降级，恢复动作可用，普通任务不会误派或假报在线可执行 |
| R04 | 新EXE/DLL缺失、安装中断 | 已核验事务自动恢复完整旧目录，无新旧文件混用，版本登记对应旧包 |
| R05 | 守护/更新器崩溃、断电 | 重启后对账同一事务，不重复安装；旧ID、密钥和配置保留 |
| R06 | 错误hash/签名、未知包、路径嵌套 | 拒绝自动替换，保留现场与明确错误，不影响其他进程 |
| R07 | Windows策略与平台差异 | Windows10/11原策略下签名组件能运行，无PowerShell7也可恢复；不关闭保护 |
| R08 | 请求方未授权或在黑名单 | 恢复入口同样拒绝，返回结构化授权状态；不得借恢复自点首次授权 |
| R09 | 所有远程入口不可用 | 本机/办公执行一个已签修复入口，完成诊断和旧版恢复，再原ID实调 |
| R10 | 长期稳定与故障循环 | 两Windows及六机持续心跳、反复重启/重连/升级失败恢复均有真实记录；不凭短时连接通过 |

下一版只有上述恢复门禁通过后才发布。先在隔离环境和一台Windows验证，再同一可信产物更新另一台；不能在100台上首次发现不可恢复升级。
