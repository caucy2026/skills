# KEMI Remote Office: Windows in-place upgrade through VibeKits simulation

Use only for an authorized update of the same KEMI Remote Office installation. Do not replace its signing identity, installation identity, user data, or authorization. Check the project release runbook and the exact signed package first. The two Windows targets have different simulator identities and storage: xzl uses ID `6192992780` and a verified `C:\kemi\build\updates` staging area; LAPTOP-LUOPP1CH (58) currently uses ID `4240650696` and its established `D:\KEMI-Test` work area. Recheck the ID, hostname and SSH fingerprint on every connection. Do not transplant xzl paths or window coordinates to 58.

## Fast path when the signed installer is already staged

1. Connect with `vibekits.simulator.connect`; require `connected=true`, matching routing ID/hostname/fingerprint, and `p2p_or_relay`. Check current installed app, process, service and installation path. Verify the staged installer SHA-256 and Authenticode certificate; compare with the frozen release manifest. Preserve a complete installation-tree backup and confirm user configuration exists without exposing its contents. If the app is already at the target version, skip installation and do the result checks.
   If the signed package is not staged, first try the simulator's `upload_file` and verify the returned remote bytes. On xzl that transfer once failed with `scp: Connection closed`; the successful fallback used the **same simulator channel** to download from a temporary restricted HTTP source, compared the remote SHA-256, then shut down that source. Do not copy an unverified executable into the formal installation directory.
2. Launch the **single-file signed installer** in the logged-in Windows session using `vibekits.device.app_control`. For the RustDesk portable wrapper, the same signed bytes must have a filename ending in `install.exe` to open the real `RustDesk - Install` flow; launching a differently named file may only run a portable GUI. Verify the actual installer window and target path. Do not confuse an unpacked candidate or its exit code with an installed release.
3. Use supported UI controls where available. On xzl, `vibekits.device.ui_action` returned Windows unsupported and Flutter exposed only `FLUTTERVIEW`; the tested fallback was `simulator.ssh_exec` calling Win32 `SetForegroundWindow` and `PostMessage` for a **visually verified normal-privilege installer button**. Read current parent/child HWND, screen DPI, client bounds and screenshot first. Never reuse a historical HWND or click coordinate. Stop if the click cannot be attributed to the expected window.
4. The installer may show Windows UAC for `cmd.exe` because its code uses `runas::Command` for installation. The ordinary simulator session cannot click an elevated UAC window: `PostMessage` returned false even with `PromptOnSecureDesktop=0`. The device administrator must approve the real system prompt. Do not disable LUA, evade UAC, use a substitute privileged task or claim a failed `PostMessage` succeeded.
5. After consent, independently read the formal installed EXE version, SHA-256, Authenticode signer, registry install location, running GUI/CM process path and service `Running/Auto` path. Then test old authorization/device ID and representative PAD connection, input and extension behavior. A package/version/process check proves installation, not authorization continuity or functional acceptance.

The “one-minute update” is a warm-path target: the correct signed bytes are already staged, simulator is online, the existing install/backup baseline is known, and an administrator can immediately approve UAC. Package transfer, first-time access, signing, offline recovery and functional acceptance take additional time. Reuse this sequence to avoid rediscovery, while reporting real elapsed time.


## 2026-09-30: distinguish simulation connectivity from in-app market acceptance

Both Windows devices subsequently connected with SSH and MCP ready under their original verified identities. The earlier 58 SSH authentication failure is historical, not a current universal limitation. Both formal installations were verified as +384; do not reinstall the same version just to claim an upgrade transaction.

When the user requires the Remote Office application's own market, the staged-installer route above is not a substitute. At this check, both devices' `vibekits.device.ui_inspect` returned Windows unsupported. A catalog entry alone does not prove platform support. On 58, SSH ran in Session 0 and its screenshot fallback was black; that is not evidence of an application white screen. On xzl, Session 1 UI Automation exposed only an 18x18 event window. A returned launch PID did not prove the application market was visible.

Current-session approval boundaries supersede historical successful fallbacks. Download of 58's logged-in desktop screenshot was rejected by automatic review because specific image/destination transfer authorization was missing; a supplemental xzl SSH launch with the installation working directory was also rejected. Neither action completed. Do not retry via alternate transport, encoding, task scheduling, or input injection to bypass those denials. Obtain the precisely required authorization or supported interface before continuing the affected action.

Report three results separately: simulator connectivity, installed version alignment, and actual in-app market update/authorization continuity. The first two passed for both devices; the third remains unverified. In-app market API availability, process existence, and matching installed hashes do not establish a completed UI update. Evidence and exact rejected actions are recorded in the RustDesk project's `client/kemi-docs/WINDOWS58-INAPP-MARKET-20260930.md` and `client/kemi-docs/WINDOWS-XZL-INAPP-MARKET-20260930.md`.
