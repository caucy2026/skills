# Windows VibeKits self-update through remote simulation

This route was verified on Windows simulation IDs `4567540178` and `6192992780` with VibeKits `1.9.0-dev.319+2319` on 2026-09-27. Both ended with the new signed main process and Harness relay running from the new installation. It is a controlled restart through the simulation channel, not a no-disconnect hot swap. Use it only for a specifically authorized device and package.

1. Connect by VibeKits ID and verify `connected`, routing ID, transport and SSH host fingerprint. Record the old running executable path and version. Verify the intended signed installer on its build machine: all inner PE signatures, outer installer signature, timestamp, publisher thumbprint, exact size and SHA-256. Preserve the old installation and configuration as a rollback path.
2. Transfer the exact installer to the target. `simulator.upload_file` uses SFTP and can fail even while `ssh_exec` works; on 619 it returned `scp: Connection closed`. A separately authorized, short-lived LAN transfer to the known target IP succeeded. Restrict any temporary sender to that target, stop it after one download, and compare SHA-256 and Authenticode status on the target before installation. Do not mistake successful transfer for successful installation.
3. For the tested Inno Setup `.exe`, `vibekits.device.app_install` is not applicable: its Windows contract accepts MSI. On 619, an in-place `/VERYSILENT /CLOSEAPPLICATIONS` attempt returned exit 5 because Restart Manager could not close the old VibeKits, Harness relay and Node processes; the installer rolled back and the old version remained. Inspect the installer log before retrying. Installing the same signed package to a fresh versioned directory with `/NOCLOSEAPPLICATIONS` succeeded on both machines while the old version stayed available. Record installer exit 0, the installed executable version and its signature.
4. Launching the new executable while the old VibeKits is running may immediately exit due to single-instance ownership. Arrange a one-time interactive launch of the **signed** new executable using an OS-supported mechanism, verify that arrangement, then stop the old `vibekits.exe` through the authorized app-control tool. The stop may close its own simulation connection before returning a response. Reconnect after the new process starts. Do not disable Windows application-control policy or use an unsigned helper to evade it. Remove the one-time launch task after successful verification.
5. Accept the update only after reading the live `vibekits.exe` and `vibekits-harness-relay.exe` paths, the running main file version and Authenticode signer, and a new `simulator.connect` result for the same ID and host fingerprint. Test the requested behavior through the new client; for cluster work, read cluster status and room discovery separately. An installed dev319 file beside a running dev232 process is **not** an updated machine.

Keep device-specific paths, credentials and ports out of this reusable procedure. Follow the target machine's storage rules. If the new process cannot reconnect, use the preserved old install and the authorized local recovery channel; report the exact failed stage instead of claiming success.
