# 动态 ADB 端口状态不一致事故排查

适用：connect 返回 connected=true、adbReady=true，但 adb connect 被拒绝、offline 或找不到设备。

## 已观察的事故

2026-10-03，同事连接 PAD63 ID 1986011413 后报告 127.0.0.1:61008 连接拒绝。复核时旧端口无监听；重新连接取得 127.0.0.1:61367，随后实际 ADB 读取到 Android 12、KEMI VibePads S1 和宿主 dev462/versionCode 2462。此结果说明复核当时新隧道可用，不能据此断言同事操作错误、原状态从未错误或设备永久正常。历史端口只作事故证据，禁止作为固定地址。

## 最短排查顺序

1. 检查当前控制端桥可用，不打印 token；核对 connect 的嵌套结构、目标 ID、身份和 p2p_or_relay。
2. 保存本次响应的 adbSerial、时间和 connection_status。只检查这个本机端口是否监听，不扫描无关端口。
3. 用本次串口执行 adb connect、get-state，再读取型号、Android 版本和宿主 versionCode/versionName。状态必须是 device，且实际身份符合目标，才可报告 ADB 可用。
4. 旧端口无监听或连接已失效时，通过原 ID 重新 connect 一次，严格采用新返回的串口，再重复实际读取。禁止反复连接旧端口、重置设备身份、清除授权、重装 APK 或杀掉共享 ADB server。
5. 新端口仍失败：分别记录桥调用、监听、ADB 握手、目标读取失败在哪层；读取已有仿真诊断和有界日志，不把在线心跳当作 ADB 成功，也不无证据归咎同事。新端口有监听也不等于目标 adbd 可用。
6. 宿主升级可能切断旧流。安装报空错误时先重连并查包管理器实际版本，不能仅凭 install 退出码重复覆盖。执行升级仍遵守既有授权与宿主恢复要求。
7. 结束只断开自己使用的串口和目标会话，不影响同事的控制端、ADB server 或其他设备。

## 验收与报告

报告必须分开列出：仿真连接结果、本次动态串口、ADB get-state、真实目标读取和未验证边界。只有完成实际读取才能写“远程 ADB 可用”。若 adbReady=true 但实际读取失败，明确报告状态不一致并保留失败层证据，不能给假成功。
